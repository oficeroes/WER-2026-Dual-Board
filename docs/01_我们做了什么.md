# 01 · 我们做了什么：从“一条线读对方地址”到两块板 WiFi TCP

> 这一页讲“过程”。结论和原理见 [`02_双板通讯原理.md`](02_双板通讯原理.md)；安装见 [`04_安装步骤.md`](04_安装步骤.md)。

## 1. 最初的问题

用户的原话大意是：

> 两块 SKCON9 用一条线连接各自 1 号 I/O 端口，主板 1 能不能通过“读取数据/写入数据（地址+数值）”
> 直接读/改主板 2 的某个地址？
>
> 另外，有些传感器“既能收又能发”，能不能用传感器本身做两板通讯？

这两个问题听起来都像“软件没开放”，所以我们从手册、APK、固件、实测四条线同时查。

## 2. 先说结论

| 想法 | 结论 | 一句话原因 |
|---|---|---|
| 一条线连两板 1 号口，A 直接读/改 B 的“数据地址” | ❌ **不可行** | “地址 1~128”是**本机** STM32 内部 Flash 的 128 个槽位，不是内存地址；端口不是存储总线 |
| 用传感器自身发射做两板通讯 | ❌ **固件不支持** | STM32 自主轮询采样；用户“读取”只读缓存，不能调制发射时序 |
| A `set_do` 输出电平 → B `get_ai/get_touch` 读电平 | ✅ 可行（低速） | bit-bang 自定义协议；需要自制两针线 |
| 声音（扬声器→麦克风）/ 光（彩灯→光敏） | ✅ 可行（信标级） | 零接线/少接线，但速率只有几~几百 bit/s |
| USB-C 当 ADB 用 | ❌ 不是 ADB | 实际是 **CH340 串口**（COM3，937500 8N1） |
| 机器人上纯 Python `import socket` | ❌ 不可用 | CPython 3.4 没有 `_socket` C 扩展 |
| **C 用户程序 + libc socket** | ✅✅ **最终方案** | 8890 下发 C → 机器人本机 gcc 编译 → JNI 加载 → 直接 `socket()` |
| 两块板 WiFi TCP 直连 | ✅ **真机成功** | 10/10 ping；4 KB 回显 ≈ 1.1 Mbps |

## 4. 我们具体做了什么

### 4.1 把“数据地址”这件事查到底

- 查 `Robot.h`：`SetEE/GetEE` 的签名只有 `(addressId, value)`/`(addressId)`，**没有目标设备/端口参数**。
- 查生成器：`robot.get_ee(地址)`、`robot.set_ee(地址,值)`，同样没有总线/从机概念。
- 查手册：12 路 I/O 是 AI/DI/DO/UART/I²C 传感器口；128 个“读写数据”是本机掉电保存区。
- 查 STM32 固件：EEPROM 在本板 Flash（约 `0x0801F000`，128×32B）；4 个帧处理函数都是内部外设处理，**没有“把端口数据转发到 I/O 口 UART”的分支**。
- 查端口：用户层没有裸总线/端口模式 API；`setSendCmd/setTTLCmd` 只能把字节写进板内 32B 帧的固定槽载荷，不会转发到另一块板。

→ **不是权限问题，是物理/固件层没有这条路。**

### 4.2 把机器人的真实运行环境测出来

实验 05 的 20 行输出：

```text
time=1  math=0  sys=1  os=1  socket=0  threading=1  struct=1  json=1
random=0  subprocess=0  serial=0  ctypes=0
py=3.4.5 (default, Jan 18 2017, 19:44:59) [GCC 4.8]
socket=0
No module named '_socket'
```

含义：

- 能用：`time / sys / os / threading / struct / json` + 纯 Python stdlib；
- 不能用：`socket / math / random / subprocess / serial / ctypes`（没有可动态加载的 `.so`）；
- 用户程序必须兼容 **Python 3.4**：不能用 f-string、类型注解等新语法。

### 4.3 找到 USB-C 这条“被忽略的线”

- 设备管理器显示 `USB-SERIAL CH340 (COM3)`，`adb devices` 为空；
- 官方 PC 软件用 `LibUart` 以 **937500 bps、8N1** 打开 `COMx`；
- 握手帧：发 `AA 55 00 08 6F B0 01 00 00 00 01 28`，收 `AA 55 00 09 6F B0 01 00 00 00 00 01 29` → **握手成功**；
- 官方软件就是用这条线下载程序；文件协议（AA55 帧、1,1 请求、1,3 分块、1,4 结束）已全部解出。

### 4.4 找到 C 用户程序这条“能跑 socket”的路

8890 文件通道支持 `fileType=20`：

1. PC 把 `.c` 源码打成 zip 发到机器人；
2. 机器人侧 `handleProgramZip` 解压、落库；
3. 用机器人本机 **gcc4.8.2** 编译成 `.so`；
4. JNI `JCC_Main` 在 Controller 进程内加载；
5. C 程序直接调用 libc 的 `socket() / connect() / send() / recv()`。

这条路**不需要 root、不需要 ADB、不需要改系统**。W4 探针在真机上连到 PC，证明通道成立。

### 4.5 两块板真机跑通

2026-11-12 12:51，两块 SKCON9 在同一 /23 网段：

- A `192.168.46.109`，B `192.168.47.199`；
- 通过 8890 下发 `W5SERVER.c` / `W5CLIENT.c`（2,334 B / 2,608 B，均回 `160,3`）；
- B 的 client 连 A 的 8888 成功；
- **10/10 次 PING 回显正确**（RTT min 7.75 / avg 34.92 / max 63.61 ms）；
- **4,096 B 回显成功**（往返 57.8 ms ≈ **1,134 kbps** 双向）。

### 4.6 把它变成“积木”

用户不写 C、不写 socket。我们把整条链路封装成 **4 个原生积木**：

1. 设置对方主板 IP；
2. 发送 [值] 到地址 [1]；
3. 接收地址 [1] 的信息；
4. 把地址 [1] 的信息保存到读写数据。

实现方式：

- 积木生成 Python 时，在 `robot = Robot()` 之后自动注入一段 prelude；
- prelude 用 `os.system` / `fork+execv` 调机器人自带 gcc，把内嵌的 C 网络助手编译到 App 私有目录（`/sdcard` 是 noexec）；
- C 助手用 **UDP 8990** 收发，行协议 `S ip addr val` / `R addr val`；
- Python 侧维护“地址→最新值”字典；收到新值时自动写 EEPROM（同一地址最快 1 秒写一次、只在变化时写）；
- 程序重启后还没收到新数据时，回读 EEPROM 旧值；从没写过的地址读出 0。

用户真机确认：**积木 → 两板通讯 → 自动写入读写数据 → 重启回读** 端到端成功。

## 5. 我们没做什么（以及为什么）

| 没做 | 原因 |
|---|---|
| 改 Android / root / 刷机 | 风险高、可能变砖；比赛设备不值得 |
| 用 testkey 拿 system UID / 开 ADB | 理论路径存在，但属高风险改造；本项目没有执行 |
| 让机器人在“没运行程序”时也能收 | 需要 Android 常驻服务，属高风险改造 |
| 远程自动起跑用户程序 | 没找到 `startRunning` 的远程入口；目前需屏幕手动点 |
| 把 8890 当“攻击面” | 只在自己队伍的设备上做实验；不干扰其他队伍 |

## 6. 一句话

> **不是“把端口变成网线”，而是“用机器人自己的 gcc 写一个 C 网络程序，再让积木在 Python 里调它”。**

这就是两块 SKCON9 能跑 WiFi TCP、而且不需要 root 的原因。
