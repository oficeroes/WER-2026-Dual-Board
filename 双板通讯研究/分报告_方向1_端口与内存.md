## 1. 背景与任务边界

用户设想（方向1）：两块 SKCON9 用一根线连各自"1 号端口"，主板1 用自带"读取数据/写入数据（数据地址+数值）"功能，直接读取或篡改主板2 的某个地址，实现"数据篡改式通讯"。

本报告回答三件事：
1. "读写数据"到底是什么、边界在哪（§2）；
2. 这个设想在硬件/固件/API 三个层面缺什么（§3）；
3. 在现有器材与 API 下**真正能落地**的两板有线通讯方案、电气安全与最小实验（§4~§7）。

> 说明：`BlocklyC_V103.apk` 是本机侧（MTK Android）配套 App 之一（PC 软件 `Constants.UPDATEPATH` 指向它：`逆向资料/decompiled/Assembly-CSharp.decompiled.cs:110829-110831` VER=103）。本报告用它做**辅助证据**（端口/协议/EE 界面均在本机侧），不作主证据；二进制/固件本体逆向由 stm32-re 负责，本文只引用、不重复。

## 2. A：把"读写数据"讲透

### 2.1 功能定义【事实】

- 手册 p16 §3.6（`_分析临时/SKCON9手册/SKCON9手册_全文.txt:381-384`）：
  > "读写数据：可存储整形数据，开关机数据不会丢失。共计128 个数据。所有数据均可在界面中修改并保存，也可以通过编程软件进行读写。"
- 同段核对：SKCON5 手册 `:338-341` 同样是"共计128 个数据"；SKCON2 手册 `:325-327` **没有写数量**（老型号实现只有 20 格，见 §2.3）。
- 类别归属：手册把"读写数据"列在**内置传感器**里（`:551` "内置传感器：声强、陀螺仪、计时器、录音、读写数据"），即它是**控制器本机自带功能**，不是外置端口设备。
- 掉电保存、界面可直接改——说明是控制器板上的非易失存储区（NVM），而不是内存变量。

### 2.2 地址空间、类型与三层取值范围【事实】

| 层级 | 地址范围 | 值范围/类型 | 证据 |
|---|---|---|---|
| 手册（SKCON9/SKCON5） | 128 个数据 | "整形数据"（整数） | `SKCON9手册_全文.txt:383`；`SKCON5手册_全文.txt:340` |
| Scratch 积木 UI（Py 路线） | **1~128**（数字框硬限制） | 写值表达式在生成时被包 `robot.clamp(…,-99999,99999)` | 积木定义 `逆向资料/关键源码/myrobotrun.js:1460`（read）、`:1475`（write）`new Blockly.FieldNumber(1, 1, 128)`；生成器 `逆向资料/关键源码/myrobotpythoncode.js:543`（read）、`:548-553`（write） |
| Chart 3.0 流程图 UI（C 路线，xLua 明文） | 输入校验 **1~40** | 输入校验 **0~4095**，`ContentType.DecimalNumber` | `逆向资料/xlua明文/ui/pc_chart/chart_tips/chartReadWriteDataTipsView.lua:121-125`（地址）、`:130-140`（值）、`:68`（写值输入框 7 位）、`:168`（地址框 3 位） |
| C API | 无文档边界 | `void SetEE(int addressId, int value)`、`int GetEE(int addressId)` | `逆向资料/apk_assets/Robot.h:81`、`:84` |
| 机器人端旧代 JS 实现（对照） | `EE_MAX=19`（0~19，20 格） | 注释 `data:0~65535`；写入后 `wait(100)` 防过度写 | `逆向资料/apk_controller/walkline.js:5`、`:174-193` |

要点：
1. **【事实】三个 UI 层的限制并不一致**（1~128 / 1~40 / 0~4095 vs ±99999）。手册与 Scratch 路线是 128 个整数槽；Chart 3.0 的 C 路线 UI 只放 1~40、0~4095，说明两个前端是不同年代/不同产品线的实现，**真正的固件边界不能从 UI 反推**。
2. **【推断】"clamp -99999~99999"是生成器在 Python 代码层加的钳制**（`myrobotpythoncode.js:551`），不是固件保证；手写 Python（代码模式/纯 Python）可以绕过 clamp 直接 `set_ee(1, 10**9)`，行为未知。
3. **【推断】典型实现是 32 位有符号整数**（C API 是 `int`，Python 侧 `get_ee` 返回 int 且与 -99999~99999 匹配）；但老型号 JS 注释写 0~65535（16 位无符号），不代表 SKCON9。
4. **【事实】EE 不是"内存地址"，是逻辑槽号**：API 参数名 `addressId`（`Robot.h:81`），不是指针/偏移；C# PC 软件里搜 `EEPROM|Eeprom|SetEE|GetEE` **零命中** → PC 端软件不参与 EE 读写（EE 完全在机器人侧处理）。
5. **【待实测】初始值**：没写过的槽读出来是 0 还是旧值？`WER_VSCode_工具/api/robotApiCatalog.json:1848` 明确标"未写过的地址返回初始值【待实测】"；`WER_积木库完全手册.md:3862-3863` 建议"读出来可能是旧值/0"。

### 2.3 "仅本机"的证据链【事实→推断】

1. **【事实】API 签名里没有"目标设备/端口/总线"参数**：`Robot.h:81` `SetEE(int addressId, int value)`、`:84` `int GetEE(int addressId)`；生成器同样只拼地址（`myrobotpythoncode.js:543,552`）。**语义上只能寻址本机存储服务**，没有远程寻址入口。
2. **【事实】实现位于本机侧 MTK 的 `libRobot.so`，且是"JNI 转发到 Java 层"的薄封装**：
   - `_分析临时/stm32分析/01_elf_info.txt:81-82` 显示 `SetEE`(0x2e99,128B)/`GetEE`(0x2f19,116B) 是动态符号（同文件 `:2` 文件为 `assets_program_c/libRobot.so`，`:3` ELF ARM ET_DYN）；`:174-175` 有 JNI 入口 `Java_com_abilix_utils_ProgramAndInterfaceC_JCC_1Main/Exit`。
   - **【事实】`libRobot.so` 的 .rodata 是"方法名+参数格式串"表**：`_分析临时/stm32分析/02_syms_strings.txt:190-231` 依次列 `SetMotor`/`%s&%d&%d`、`SetDO`/`%s&%d`、`SetEE`/`%s&%d`、`GetEE`、`GetAI`、`setSendCmd`/`getSendCmd`/`getRecvCmd` 等，配合同文件 `:46` 的 `CCJ_Interface` 符号（size 824）→ 说明每个 C API 把"命令名&参数"拼成字符串、经统一 Java 桥（`CCJ_Interface`）执行。
   - **【事实】SetEE/GetEE 反汇编就是 JNI 调用模式**：`_分析临时/stm32分析/05_disasm_annot.txt:653-761` 中两者加载 `g_AbilixEnv`（JNIEnv*）并调用 PLT（`0x2298/0x22bc`），与同文件开头 `JCC_1Main`（`:3-120`）使用同一 JNI 机制。
   - **【推断】因此 EE 读写的最终实现落在 Android(MTK) 侧 Java 服务**（由 Java 再落到本地存储或再转发给 STM32，具体位置**待stm32-re 报告**定论）；但无论落在哪，它都在本机主控内部，**不经过 RJ11 端口总线**。
3. **【事实】屏幕上"读写数据"界面 = 同一套本机 EE 读写**：`BlocklyC_V103.apk` dex 里有 `EepromActivity`/`activity_eeprom`/`'robot.getEE'`/`'robot.setEE'`/`'EEPROM'` 等字符串（提取记录见 `_分析临时/研究证据/方向1/apk_scan.txt` 与 `apk_scan3.txt`）；布局为 GridView 列表（`_分析临时/研究证据/方向1/BlocklyC_V103_apk/res_layout_activity_eeprom.xml`，二进制 AXML）。
4. **【事实】环境采集会把标定值写进 11~20 号槽**（`SKCON9手册_全文.txt:683-685`："采集的值会依次存储在SKCON9 数据位置11-20"），本队样本程序也用 `get_ee(9/10)` 读标定值（`逆向资料/样本程序/experiment.py:158-159`、`PI.py:852-853`）。→ EE 是**本机标定数据存储**，换一台控制器就换一套 EE（`WER_积木库完全手册.md:3863`："换了控制器（EEPROM 在控制器上）"）。
5. **【推断】EE 物理位置**（STM32 内部 FLASH 仿真/外部 EEPROM 芯片/MTK 分区）尚未定论 → **【待stm32-re】**。但无论在哪，它只挂在**本机**主控上；这是方向1 无法成立的物理根因（见 §3.3）。**这一点不依赖 EE 位置结论**：即便 EE 在 STM32 上，端口线也不会把 STM32 的存储总线引出来。

### 2.4 越界/负数/异常行为（证据现状 + 待实测清单）

## 3. B：方向1 工程可行性论证（主板 A 直接读/写主板 B 的 EE？）

### 3.1 端口侧硬件与数据通路（事实清单）

1. **【事实】双处理器架构**：MTK6580（1.3GHz，4G Flash/512M RAM）+ STM32F103VET6（72MHz，512K Flash/64K SRAM）（`SKCON9手册_全文.txt:133-134`）。
2. **【事实】12 路 I/O（RJ11）能力**：AI、DI、DO、**UART×10**、可复用 **I²C×2**（`SKCON9手册_全文.txt:135-138`）；端口"具有识别传感器类型的功能"（`:234-236`）。
3. **【事实】电机口 4 路（RJ11）**：闭环，**输出电压=电池电压**（7~8.4V），单路最大 1.5A，支持编码器回读（`:139-141`、`:160-161`）。
4. **【事实】SERVO 1 路（RJ11）**：**485 总线**，最多 11 个智能电机（`:142`）。
5. **【事实】MTK 与 STM32 之间是一条内部串口 + 私有帧协议**（来自本机侧 App 证据，非端口）：
   - `BlocklyC_V103.apk` dex 含 `SerialProcess`/`SerialPort`/`org/winplus/serial/utils/SerialPort`、`initSerialPort successful!`、`nPort`/`nSpeed`/`baudrate`（`_分析临时/研究证据/方向1/apk_scan.txt`）；
   - 协议命令名、错误类型、固件升级通道：`CMD1_0..CMD1_4`、`CMD1_A0`、`CMD1_A1`、`CMD2_0..CMD2_4`、`CMD_BOOT`、`CMD_ONE`、`CMD_RESET`；中文串"包头出错:"/"校验位出错:"/"类型出错:"/"关闭串口"/"老协议"；`UpdateStm32`；`/Download/Blockly/update/stm32.bin`（`_分析临时/研究证据/方向1/apk_scan.txt`、`apk_scan3.txt`）；`libserial_port.so` 在 APK 内（同文件清单）。
   - 端口读数通过 **`getrAI0..7`/`getrAII0..7`/`getsDO`/`getrCmd`/`getsCmd`** 一类接口取得（`apk_scan3.txt`），也就是：**MTK 只是"发命令+收结果"，真正碰 RJ11 引脚的是 STM32 固件**。
6. **【事实】用户程序可见的 API 里没有任何裸总线/端口模式/从机模式方法**：`WER_VSCode_工具/api/robotApiCatalog.json` 共 80 个方法（任务交底），只有 `get_ai/get_touch/get_gray/set_do/set_ee/get_ee/...`；**没有 uart/serial/send/receive/i2c/raw gpio**（任务交底 + §2 生成器全表核对）。
7. **【事实】C API 有一个"未暴露"的通用命令槽**：`void setSendCmd(int cmd,int index,int value)`、`int getSendCmd(int cmd,int index)`、`getSendCmdBuffer/getRecvCmd/getRecvCmdBuffer`（`Robot.h:144-153`）。`libRobot.so` 中确实存在这些符号（`_分析临时/stm32分析/01_elf_info.txt:125-133`），另有 `hexString2bytes`/`toUpper`（`:127-128`）→ 说明它按"命令号+索引+值（可含 hex 字符串）"与下层交互。**但：积木库/生成器/API catalog 全都不暴露它们**（`WER_积木库完全手册.md:2517` 明确列为"没有积木的函数"），用户 Python 程序无法调用。
8. **【事实】EEPROM 读写是"存储服务"而非总线传输**：见 §2.3。
9. **【事实/推断】C API 层是"命令字符串 → Java 桥"**：`libRobot.so` 的 `.rodata` 是"方法名+参数格式串"表（`_分析临时/stm32分析/02_syms_strings.txt:190-231`），统一经 `CCJ_Interface`（`01_elf_info.txt:46`）执行；`SetEE`/`GetEE`/`SetDO`/`GetAI`/`setSendCmd` 都是同一张表里的条目 → **用户程序的所有硬件动作（包括 EE、端口 IO）都只是向本机 Java/固件层发一条命令，命令的"目标"永远是本机**。【待 stm32-re 定论：Java 桥之下哪些命令转给 STM32、EE 最终落在哪】

### 3.2 逐条论证：为什么"一根线读/写对面地址"不成立

1. **寻址层面的缺失**：EE API 的参数只有"槽号+值"，没有"目标设备/端口/从机地址"。两块板之间要通讯，至少需要"我这条报文是发给谁/哪个地址"的协议字段，而 SKCON9 用户 API 里没有任何报文/目标概念。【事实：§2.3-1】
2. **物理层面的缺失**：RJ11 口引出的是 STM32 的 GPIO/ADC/UART/I²C 引脚（手册 `:135-138`），**不是 STM32/MTK 的存储总线**。EEPROM 挂在主控上（MTK 侧 libRobot.so 实现 EE 读写，`01_elf_info.txt:81-82`），它的地址线/数据线/SPI/I²C 走主板内部，**没有引到 RJ11**。所以"从端口线去访问 EE"在物理上就没有通路。
3. **方向/角色层面的缺失**：用户侧所有端口操作都是"**主机**对传感器/执行器"的语义：读 AI/DI（输入）、写 DO（输出）、自动识别传感器类型（手册 `:234-236`）。**没有任何"从机模式"或"把本机内存暴露成外设"的开关**。两块 SKCON9 都是主机 → 两个主机之间没有协议栈，也没有协商从属关系的 API。
4. **固件层面的缺失**：RJ11 的 UART/I²C 是 STM32 固件**为特定传感器/模块准备的**（`UART×10`/`I²C×2` 是端口能力描述；实际端口模式由固件按自动识别结果决定）。用户程序只能在"已经被识别出的传感器类型"上取值，**不能命令固件"把端口 1 切成串口主机/UART 透传"**。【事实：API 无此方法 + 手册只描述识别行为】【推断：模式选择在 STM32 固件内】
5. **协议层面的缺失**：MTK↔STM32 的私有帧协议（`CMD1_*/CMD2_*`）是**板内**协议，目标永远是"本机 STM32"（因为帧里没有设备地址字段的证据，且 App 只连本机串口）。即使有 `setSendCmd` 这类底层命令槽（C 层未暴露），发出的也只会是**本机 STM32 命令**，不是"对面主板"。
6. **"数据篡改"的对象错位**：用户以为"地址"是内存地址，可以隔着线改对面数值；实际"地址 1~128"是**本机持久存储的槽号**，其读写由本机程序/本机屏幕发起。对面主板上的 EE 只会在**它自己的程序**调用 `set_ee` 时改变——外部信号无法让它执行 `set_ee`。

### 3.3 "缺哪一环"——把它说清楚

要让方向1成立，必须同时补齐 4 环，缺一不可：

| 环 | 需要什么 | 现状 |
|---|---|---|
| ① 物理通路 | RJ11 里有一对线是"存储总线"或可复用为数据总线，且电平/时序可控 | **没有**：RJ11 是 GPIO/ADC/UART/I²C 传感器口（`SKCON9手册:135-138`），EE 总线未引出 |
| ② 端口模式控制 | 用户能把端口切成"自定义 UART/I²C 主/从"或"GPIO 裸操作" | **没有**：API 无此方法（§3.1-6）；C 层 `setSendCmd` 未暴露（§3.1-7） |
| ③ 从机/被访问方 | 主板 B 能把本机内存/EE 暴露成"从设备地址空间"，并响应外部读改写 | **没有**：无从机模式 API；两板都只做主机 |
| ④ 远程存储协议 | 一条"读地址/写地址+校验"的线上协议，双方都实现 | **没有**：EE 是纯本机服务（§2.3），线上协议只存在板内 MTK↔STM32 |

**一句话**：方向1 缺的不是"接线技巧"，而是"**端口→内存映射**"这一整层（硬件未引出 + 固件不支持 + API 未开放 + 协议未定义）。当前产品架构里，端口线只承载"传感器/执行器"语义的数据，不承载"另一台主控的内存/存储"语义。

### 3.4 有没有"后门"例外？（需交叉验证，不改变结论）

1. **`setSendCmd/getRecvCmd`（C API 未暴露）**：即使通过某种 C 编程模式调用到，它面向的是**本机 STM32**（板内协议），不是另一块板。→ 对方向1 无用。【推断，待 stm32-re 验证帧语义】
2. **STM32 固件升级通道**（`stm32.bin` / `UpdateStm32`）：这是"刷新本机固件"的通道，不是通用通讯 API；要靠它实现两板通讯=改固件，属于"改造产品"而非"用现有功能通讯"，且风险极高（变砖）。→ 不建议。【推断】
3. **APK 层/ADB 层更高权限**：`Constants.COMMANDEXEC = "adb.exe"`（`逆向资料/decompiled/Assembly-CSharp.decompiled.cs:110819`）——**事实**：PC 软件常量里定义了 adb；但全仓库 grep 在 C# 反编译与 xLua 明文里**找不到调用点**（仅定义处 1 处 + `asmcs_ascii.txt:5268` 字符串），且 `C:\platform-tools\adb.exe` 存在但当前无设备。→ 【推断】更像遗留/未启用代码，**不能作为"官方支持 adb"的证据**；adb 高权限路线交 runtime-alt 汇总，本报告只记录证据。
4. **`get_ai` 读原始 AD / `set_do` 写数字输出**：这是**唯一真实可用**的端口级电气接口 → 支撑 §4 的 bit-bang 方案（替代路线，而非方向1 原设想）。

**方向1 判定：不能（现有官方功能/固件/API 下）。** 若未来固件开放"端口透传/从机模式"，才可能升级为"有条件能"，但那已超出"用现有读写数据功能"的范畴。

## 4. C：实际可做的端口直连方案

### 4.1 方案1（推荐首选）：`set_do` → `get_ai`/`get_touch` 的 bit-bang 链路

#### 4.1.1 电气可行性（先讲风险，再谈接线）

| 项 | 现状/要求 | 依据 |
|---|---|---|
| 电平 | **未知**：STM32F103 是 3.3V 器件，但端口可能经驱动/电平转换到 5V；**必须实测** | `SKCON9手册:133-134`（型号）；手册无电平表（事实） |
| 驱动能力 | **未知**；DO 大概率是 MCU GPIO 或经三极管，source/sink 能力需实测 | 手册无 | 
| 共地 | **必须共地**（单端电平判读的前提）；两块板各自电池供电，GND 需通过线缆连通 | 【推断】 |
| 串联电阻 | **信号线必须串 1kΩ**（限流、防止两侧同时驱动时烧 IO；3.3V/1k≈3.3mA，安全） | 【推断，工程惯例】 |
| 长线 | 建议 ≤1m 短线（杜邦/网线单股）；长线加 100Ω 串阻+考虑干扰 | 【推断】 |
| 高阻/上拉 | DO 关闭时可能是高阻或下拉，AI 输入可能带上/下拉；**决定"空闲电平"与阈值**，必须实测 | 【待实测】 |

**核心风险（详见 §5）**：两块板端口都带"传感器自动识别"（手册 `:234-236`），识别针/信号针可能被**双方固件同时驱动**；标准 RJ11 直通线还会把两板 VCC 短接。→ 必须自制线：**只连 GND + 信号**，VCC 与识别针悬空。

#### 4.1.2 接线示意（推荐 3 线：单向 + 反向 + 共地）

```
        板 A（发送为主）                          板 B（接收为主）
   ┌──────────────┐                          ┌──────────────┐
   │ 端口1  PJ11  │                          │ 端口1  RJ11  │
   │  SIG_A(DO) ●─┼──[1kΩ]───────────────● SIG_B(AI/DI) │
   │  GND      ●─┼──────────────────────● GND            │
   │  AI_A     ●─┼──[1kΩ]───────────────● DO_B(SIG)      │  ← 反向线（握手/回传用，可选）
   │  VCC      ○  │  (不接！)             │  VCC      ○  │
   │  ID/识别  ○  │  (不接！)             │  ID/识别  ○  │
   └──────────────┘                          └──────────────┘
```

| 线 # | 板 A 端 | 板 B 端 | 说明 |
|---|---|---|---|
| 1 | GND 针 | GND 针 | **唯一必须共用**的线；先测两板地电位差 |
| 2 | 端口1 的 DO/信号针 | 端口1 的 AI/DI/信号针 | 串 1kΩ；单向 A→B |
| 3（可选） | 端口2 的 AI 针 | 端口2 的 DO 针 | 串 1kΩ；反向 B→A，用于 ACK/半双工 |
| — | VCC | — | **禁止连接**（两套电源顶牛/倒灌） |
| — | 识别/ID 针 | — | **禁止连接**（双方固件可能同时驱动） |

> RJ11 是 6P4C：只有中间 4 针有线，具体哪根是 VCC/GND/SIG/ID **手册未给**（grep 无引脚定义），必须按 §5 的测量清单确认后再接线。

#### 4.1.3 协议设计（脉宽编码 + 自同步帧，抗抖动优先）

设计目标：在"每次 API 调用可能几 ms~几十 ms、sleep 有抖动"的条件下可靠传 1~几个字节。

- **物理层**：单线电平，**脉宽编码（PWM/类 1-Wire）**，T = 基本时隙。
  - 前导/同步：低电平 `8T`（区别于任何数据位），接收端检测到长低电平后开始采样。
  - 数据位（每 bit 固定 `4T` 窗口）：`0` = 高 `1T` + 低 `3T`；`1` = 高 `3T` + 低 `1T`（按"高电平宽度"判决，抗时钟漂移）。
  - 字节：LSB first，8 bit + 1 bit 偶校验（或整帧 CRC4）。
  - 帧：`SYNC(8T) + 0xA5 + addr(1B) + data(1B) + CRC4(4bit)`；反方向帧头用 `0x5A` 区分。
- **为什么脉宽而不是曼彻斯特**：曼彻斯特每位都要求**精确边沿时刻**，而发送端靠 `set_do()+sleep()` 产生边沿，**边沿抖动可能远大于位宽**；脉宽编码只要求"两个跳变之间耗时成比例"，对边沿绝对时刻不敏感【推断，待实测抖动】。
- **半双工握手**（有第 3 根反向线时）：
  1. A 发 `REQ` 帧（含 seq、命令、数据、CRC）；
  2. B 解码成功后在**自己的 DO** 上回 `ACK` 帧（含同一 seq）；
  3. A 在超时（如 2s，用 `get_timer_ms`）内未收到 ACK → 重发，最多 3 次；仍失败则报错。
  4. 无反向线时退化为**单向广播**（只能 A→B，不能 B→A 确认）。
- **接收端采样策略**：`while True: v=get_ai(port); t=get_timer_ms(timer); 记录 (t,v)`，用状态机找 SYNC→逐位测宽；不依赖固定周期，只依赖时间戳。若只有 `get_touch`，则用"边沿+脉宽"方式但需先测其消抖/最小脉宽。

#### 4.1.4 速率估算（给 Lead 写程序时定 T 用）

已知【事实】：
- 官方/本队规范要求轮询循环加 `time.sleep(0.01~0.05)`：`WER机器人代码生成_给AI的说明书.md:435`；
- 样本程序大量使用 `time.sleep(0.01)`/`0.02` 轮询（`逆向资料/样本程序/main.py:143-146,150-153` 等 52 处）；
- `get_ai` 是"原始 AD 计数、无滤波"（`WER_积木库完全手册.md:1245-1250`），每次调用是一次板内协议往返【推断】。

估算（T 需在 Step1 实测后定）：

| 假设单次 `set_do`/`get_ai` 往返 | 建议 T | 位宽 4T | 一帧(1+4B+4bit≈37T+8T) | 有效吞吐 |
|---|---|---|---|---|
| ~5ms（乐观） | 20ms | 80ms | ≈0.9s | ≈1.1 B/s |
| ~10ms（现实） | 40ms | 160ms | ≈1.8s | ≈0.55 B/s |
| ~20ms（悲观，含 sleep 抖动） | 80ms | 320ms | ≈3.6s | ≈0.28 B/s |

→ **保守设计目标：0.3~1 B/s**；只适合传"命令/状态/参数"（如坐标、模式、开关），不适合传图像/长文本。若实测 `get_ai` 往返能压到 1~2ms 且 sleep 抖动小，可把 T 降到 5ms，逼近 5 B/s（仍很慢）。【待实测】

#### 4.1.5 关键未决问题（决定方案1 能否成立）

**Q1（最关键）：空置端口（未识别到传感器）时，`get_ai` 是否还能反映外部电平？**
- 【事实】手册只说界面显示"断连立即恢复为端口xx：0"（`:234-236`），**没说 `get_ai` 的行为**。
- 若固件"未识别→返回 0"：外部电平读不到 → bit-bang 直接失败 → 必须走 **Q2 的传感器仿真路线**。

**Q2（备用路线）：仿真一个"能被自动识别"的传感器**
- 碰撞（2 线开关）最容易仿真：外部信号经 **NPN/光耦** 把信号针拉低到 GND，端口识别为"碰撞"后 `get_touch` 读到 0/1。
- 灰度（模拟）可用分压/电位器仿真，`get_ai` 读中间值做多电平。
- 代价：多一层"识别"依赖，且识别过程可能需要上电时序/特定阻抗；**先按 §6 Step1 单板自环实测**。

### 4.2 方案2：端口进 UART/I2C 模式做真串口通讯？——用户层不能

- 【事实】手册写端口具备 UART×10、I²C×2（`:135-138`）→ **硬件能力存在**。
- 【事实】用户 API 无端口模式/串口收发方法（80 方法清单；生成器无对应；`Robot.h` 也无 `UART/I2C/PortMode` 类函数）。
- 【事实/推断】端口模式由 STM32 固件按"传感器自动识别"结果决定（手册 `:234-236`；MTK↔STM32 协议命令 `CMD1_/CMD2_` 均为固定语义，未见"port mode"命令 → 见 `apk_scan.txt`）。
- **结论**：现有用户程序**不能**把 I/O 口切成 UART 主/从做两板串口；缺的是"用户可写的端口模式配置命令 + 对端协议栈"。【待stm32-re】若固件逆向发现隐藏的端口模式命令（如 `CMD1_A0/A1` 语义未明），可升级为"固件层可能，但需修改/绕过 App"，仍不算官方可用功能。
- 补充：即使能切 UART，两板都是 UART 主机（TX 对 TX）也需要交叉接线 + 共地 + 波特率一致；这些都不是现有 API 能配置的。

### 4.3 方案3：485 SERVO 总线 / 电机口 / 编码器口 —— 不能，且危险

| 通道 | 事实 | 结论 |
|---|---|---|
| SERVO（485） | 1 路 RJ11，485 总线，最多 11 个智能电机，ID+角度（`SKCON9手册:142,321-338`） | **不能**：总线协议私有、无用户收发 API；两板 485 互连会连接两套电源与两个主机驱动器 → **有烧毁风险**；智能电机 ID 还会冲突 |
| 电机口 A~D | 输出电压=电池电压 7~8.4V，单路 1.5A（`:139-141`） | **绝对不能接 I/O**：7.4V 直接加在 3.3V 器件 I/O 上会击穿 STM32；两板电机口互连=两个 H 桥输出对抗，可能烧桥；且电机口没有数据通讯协议 |
| 编码器输入 | 电机口回读编码器（模拟量，`:139-141,298-320`） | 只能读、不能发；用于两板通讯无通路 |

> **安全红线**：任何"把电机口/电池电压引到 I/O 口"的接法都禁止。SERVO/电机口实验必须由有电子经验的人在断电、限流条件下做，本方案不推荐。

| 方案 | 可行性 | 速率 | 风险 | 结论 |
|---|---|---|---|---|
| 1. `set_do`→`get_ai/get_touch` bit-bang | **有条件能**（先过自动识别关） | 0.3~1 B/s | 低（3 线+1kΩ，不接 VCC/ID） | **推荐做 MVP** |
| 2. 端口 UART/I²C 模式 | 用户层不能；固件层待证据 | 理论高 | 中（需改固件/绕 App） | 暂不做，等 stm32-re |
| 3. 485 SERVO / 电机口 | 不能 | — | **高（烧板）** | 禁止 |

## 5. D：电气安全清单（两板端口直连）

### 5.1 为什么"不能直接用一根 RJ11 直通线对插两块板的 1 号口"

1. **VCC 对 VCC**：两块板各自有 7.4V 电池（`SKCON9手册:160-161`）与稳压后的 5V/3.3V；直通线会把两套电源输出**硬短接**，轻则保护/重启，重则烧稳压器。【推断，高置信】
2. **识别/信号针双驱动**：端口会自动识别传感器（`:234-236`），识别过程很可能由固件驱动信号/识别针；两板同时驱动同一根线 → **对顶电流**（无串阻时可达数百 mA）。【推断，高置信】
3. **电平不匹配**：两板各自参考自己的 GND，不共地时电平判读无意义；共地后若一侧 5V 输出、另一侧 3.3V 输入，过压风险取决于实际电平（**必须实测**）。
4. **热插拔**：带电插拔 RJ11 会产生瞬态，可能打坏 IO。【推断】
5. **电机口/电池电压混接**=直接烧板（§4.3）。

### 5.2 必须先做的电气测量清单（按顺序，断电→上电→限流试）

> 逐项记录到 `_分析临时/研究证据/方向1/电气测量记录表.md`（本报告附带空白表）。

**Step 0：断电通断（万用表通断/二极管档，两板都不上电、不接电池）**
- [ ] RJ11 四针两两通断：找出 4 根线的分组（通常电源两针一组、信号两针一组；**以实测为准**）。
- [ ] 每针到板内电池座正/负极、USB 口 GND 的通断：判定 VCC/GND。
- [ ] 确认两板 RJ11 针序方向（卡扣朝上/朝下）一致，避免镜像接错。

**Step 1：单板上电空载电压（万用表 DC 档，只上电一块板）**
- [ ] VCC 针 ↔ GND 针：电压（预期 5.0V 或 3.3V，**实测**）。
- [ ] 信号针 ↔ GND：空闲电平（0V？3.3V？悬空？高阻无法用万用表判断，需示波器）。
- [ ] 识别针 ↔ GND：空闲电平/是否有周期性探测脉冲（示波器）。

**Step 2：功能动作时的电平（单板）**
- [ ] 运行程序 `set_do(1,1)` → 测哪根针变高/变低，电压多少；`set_do(1,0)` 再测。
- [ ] 接一个已知传感器（碰撞/灰度）到端口，读 `get_touch/get_gray` 对照，确定信号针。
- [ ] 示波器：看 DO 边沿上升/下降时间、空闲是否高阻、是否有识别探测脉冲（决定能否 bit-bang）。

**Step 3：两板对接前（里程碑，**不通过不许接**）**
- [ ] 两板分别上电，**只连万用表**：测两板 GND 之间的电位差（应为 0V；若不为 0 先查是否共地/漏电）。
- [ ] 用 100Ω 电阻跨接两板 GND，测电流（应≈0；有电流说明存在地环路/漏电，停止）。
- [ ] 确认两板端口信号空闲电平一致（都 0V 或都同一电平）后才允许接信号线。

**Step 4：最小化对接（限流）**
- [ ] 只接 GND + 一根信号线（串 1kΩ），**不接 VCC、不接识别针**。
- [ ] 先测对接后信号线电流（万用表串入，应 <1mA；异常立即断开）。
- [ ] 再跑 Step1 自环程序验证通讯；成功后再考虑加反向线。

### 5.3 操作红线（写进实验守则）

1. **禁止**：标准 RJ11 直通线对插两板任何端口；**禁止**接 VCC 到对面；**禁止**接识别针到对面。
2. **禁止**：电机口 A~D / SERVO 口 / 电池直接或间接接到 I/O 口；**禁止**带电插拔。
3. 接线改动**必须断电**；上电后先测电压再插传感器/程序。
4. 信号线**必须串 1kΩ**（两侧都串更安全）；两板共地只走一根 GND。
5. 出现发热、异味、重启、屏幕异常 → 立即断电并记录。

## 6. E：结论分级 + 最小可行实验（MVP）

### 6.1 结论分级

| 级别 | 内容 |
|---|---|
| **不能** | 方向1 原设想（A 通过 1 号口读/写 B 的 128 个数据地址、实现"数据篡改通讯"）。缺 4 环（§3.3）。 |
| **有条件能** | `set_do`→`get_ai/get_touch` 的 bit-bang 单向/半双工链路：短距、慢速（0.3~1 B/s 量级）、需自制 3 线 + 1kΩ、需先实测端口电平与"自动识别"行为。 |
| **待证据** | 端口 UART/I²C 透传（用户层不能；固件层等 stm32-re）；adb 高权限路线（仅记录证据，交 runtime-alt）。 |
| **不能且危险** | 485 SERVO/电机口作为两板连接（烧板风险，禁止）。 |

### 6.2 最小可行实验（MVP，程序由 Lead 最终编写，以下为设计）

**Step 0（零风险，先做）：单板 DO→AI 自环**
- 接线：**同一块板**，端口1 信号针 →[1kΩ]→ 端口2 信号针；两端口 GND 不额外连（同一块板已共地）；不接任何 VCC/识别针。
- 程序 A（单板）：
  1. `set_do(1, 1)`；`sleep(0.02)`；读 `get_ai(2)`/`get_touch(2)` 记录 → 期望"高电平对应读数 X_high"；
  2. `set_do(1, 0)`；`sleep(0.02)`；再读 → "低电平读数 X_low"；
  3. 循环 200 次，记录 `get_timer_ms` 差值（测单次往返耗时与抖动）；
  4. 若 `get_ai(2)` 恒 0 或恒不变 → 空置端口不可用，转 Q2 仿真路线（接碰撞开关/光耦仿真）。
- **判定标准**：X_high 与 X_low 差值显著（≥500 AD counts 或 0 vs 4095），且往返耗时 ≤10ms → 可进入 Step 1；否则记录并改协议参数/换 get_touch。
- **这一步同时回答"端口电平/驱动/是否高阻/是否被识别"**，且不会损伤第二块板。

**Step 1：两板单向（A→B）**
- 接线：GND-GND + A 端口1 信号 →[1kΩ]→ B 端口1 信号（不接 VCC/识别针）。
- 程序 A：发 5 帧 `0x55/0xAA` 交替（按 §4.1.3 编码，T 先用 40ms）。
- 程序 B：`get_ai` 原始采样 + 时间戳，打印解码结果/误差。
- **判定**：B 能解出正确字节，误码 <1/50 帧 → 通过；否则调 T/阈值/换 get_touch。

**Step 2：半双工握手（可选反向线）**
- 接第 3 根线（B 端口2 DO → A 端口2 AI，串 1kΩ）；A 发 REQ，B 回 ACK；统计往返时延。
- **判定**：3 次重传内成功率 >95%。

**Step 3：传"命令+数值"**
- 帧格式：`SYNC + 0xA5 + cmd(1B) + addr(1B) + value(2B) + CRC4`，如 cmd=1 表示"写参数"、2 表示"请求状态"。
- 完成 1 个真实用例（如 A 遥控 B 的变量/模式），记录吞吐与稳定性（连续 5 分钟无错）。
