## 0. 先看结论（TL;DR）

### H. 2026-11-12 晚：双板通讯「原生积木」+ 读写数据持久化 ✅（用户真机实测通过）

- 已把双板通讯封装成 AbilixScratch3.0（1.0.3.4）**原生积木**，共 4 块：①设置对方主板 IP ②发送 [值] 到地址 [ ] ③接收地址 [ ] 的信息（数字型 reporter，可当变量用）④把地址 [ ] 的信息保存到读写数据。用户已拖动积木实测通过（2026-11-12，m01022 任务闭环）。
- 实现路线（唯一可行，详见 §0.0-B/E）：机器人 Python 3.4.5 没有 socket/ctypes → 在生成的程序 `robot = Robot()` 之后自动注入 prelude：用 `os.system`/`fork+pipe+execv` 现场调用机器人自带 **gcc4.8.2**，把内嵌的 C 网络助手编译到 **App 私有目录**（`/data/data/com.abilix.controller/files`，因 `/sdcard` 是 noexec）再执行；C 助手用 **UDP 8990** 收发（`S ip addr val` / `R addr val` 行协议），Python 侧维护“地址→最新值”字典。
- **读写数据（EEPROM）持久化**：双向通讯的“地址 1~128”与主板「读写数据」01~128 **同一套槽位**；收到数值时自动写 EE（同一地址最快 1 秒写一次且只在数值变化时写，保护擦写寿命），程序重启后还没收到新数据时回读 EE 旧值；从未写过的地址读出 **0**（实测 121/122/123/126/127/128 全 0）。

### 0.1 方向1：一条线连两板 1 号端口，A 直接读/篡改 B 的"数据地址"

| 问题                                 | 结论              | 一句话理由                                                                                                               |
| ---------------------------------- | --------------- | ------------------------------------------------------------------------------------------------------------------- |
| A 通过端口线**直接读取** B 的 `get_ee` 地址值   | ❌ **做不到**       | "数据地址"是**本机 EEPROM 的 128 个整数槽位**，不是内存地址；两板之间没有共享存储总线，端口也不是存储接口                                                      |
| A 通过端口线**直接改写** B 的地址值             | ❌ **做不到**       | 同上；B 的数据槽只能由 B 自己的程序/界面写入                                                                                           |
| 用一条线让**两块板传数据**                    | ✅ **可以**（但方式不同） | 用 `set_do` 输出电平 → 对面 `get_ai`/`get_touch` 读电平，bit-bang 自定义协议；或改用 WiFi（见下）。底层"原始字节注入"通道已查清：只到本机 STM32、不能到另一块板（§2.4A） |
| 让 B 改自己的数据（A 发消息、B 收到后自己 `set_ee`） | ✅ **可以**（通讯建立后） | 这是"消息驱动"，不是"远程写内存"；等价于两板约定协议                                                                                        |

**方向1 的句话总结**：**"读/改对方地址"这条路物理上不存在；但"用端口线做两板通讯"是可行的，只是速率低（先按 10~20 bit/s 起步），而且必须自制只连一 GND+信号的两针线、先万用表确认引脚，不能拿普通 RJ11 线直接对插。**

> **本次逆向的补充结论（已查清，不改变主结论）**：机器人端确实存在"把自定义字节注入板内 MTK→STM32 串口帧"的隐藏通道（C API `setSendCmd`/`setTTLCmd`/`getSendCmdBuffer` 等），另有第二路串口 `/dev/ttyMT0`。但逆向 STM32 固件确认：**这些字节只落在板内 32B 下行帧的固定槽载荷里，固件没有"转发到 I/O 口 UART"的分支；`ttyMT0` 是 PC 下装/升级通道**。→ **两板"串口级"通讯在现有固件下不支持**。详见 §2.4A。

### 0.2 方向2：利用"既能收又能发"的传感器做两板通讯

| 方案 | 结论 | 速度/难度 | 备注 |
|---|---|---|---|
| **声音链路**：A 扬声器 → B 麦克风（`play`/`play_until` → `get_mic`） | ✅ **最快能验证** | 慢（音符级，几 bit/s） | 零接线、零外设；两板 10 分钟可出结果 |
| **光链路**：A 彩灯/LED/智能灯 → B 光敏/灰度/火焰 | ✅ **可行** | 中（10~100 bit/s 量级，待实测） | 需要一对"灯+光敏"模块；无电气风险 |
| **端口线电链路**：A `set_do` → B `get_ai`/`get_touch` | ✅ **可行** | 中低（10~几百 bit/s，待实测） | 最接近方向1 的"一条线"设想；需自制线+测量 |
| **WiFi 链路**：两板连同一 2.4G 路由器/热点，Python `socket` 直连 | ❌ **纯 Python 不可用（实测 socket=0）** | — | 2026-11-11 实测：运行端无 `_socket` 扩展，`import socket` 直接失败；要 WiFi 只能走 C 程序/安卓改造（§0.0） |
| **传感器自身发射**：灰度 IR LED / 红外测距 LED / 超声换能器 对射 | ❌ **固件层不支持（架构上不乐观）** | 低 | STM32 **自主轮询采样**（每帧广播、≥1.5ms 一帧），用户"读取"只读缓存、不触发发射；也没有"端口自定义串口/透传"分支。灰度对射/超声互扰可做黑盒实测，但预期不可控（§3.4） |

**方向2 的一句话总结**：**"传感器收发一体"这个观察是对的（灰度/颜色/红外/超声确实都含发射+接收），但"用传感器自身发射来通讯"在固件层没有可控性（STM32 自主轮询、无法由用户程序调制）；真正可靠的两板通讯是"用执行器当发射、传感器当接收"（声音/光链路）。**

**【实测结论（2026-11-10，已推翻原推断）】** 下载的 .py 里 **`import socket` 失败**（`socket=0`、`No module named '_socket'`），同时 `math/random/subprocess/serial/ctypes` 也不可用；可用的是 `time/sys/os/threading/struct/json`。原因：运行端只有静态编入 libpython 的 C 模块 + zip 内纯 Python 模块，没有可动态加载的 C 扩展 .so（完整 20 行结果见 `双板通讯研究/实验/实验5返回结果.txt` 与 §0.0-A）。→ **纯 Python WiFi 路线关闭**。

**【事实/待实测】若 socket 不可用**，还有一条"B 计划"：机器人端的 C 程序是**在本机用 gcc4.8.2 编译成 .so 再加载执行**的（`分报告_APK与串口协议.md` §5.1），C 代码可以直接调 `socket()` 等 libc 函数 → 绕过 Python 的 import 限制；但需要能下载自定义 `.c`（Chart 3.0 C 模式），门槛较高、合规风险也更高。

### 1.5 机器人的"内脏"：MTK ↔ STM32 双芯片结构

**【事实】** 机器人里有两颗芯片：
- **MTK6580**：跑 Android、屏幕、WiFi、Python/C 程序、显示、声音、AI 模块；
- **STM32F103VET6**：实时控制 12 路 I/O、4 路电机、SERVO 485 总线、编码器、传感器采样。

**【事实】** 两者之间靠一条**串口**通讯：设备路径 `/dev/ttyMT1`（BlocklyC/Controller 的 dex 字符串均有；`_分析临时/研究证据/运行环境/controller43_6F/dex_keywords_hits.txt` 与 `_分析临时/apk分析/提取/disasm_com_example_blocklyc_SerialProcess.txt:190`），协议实现位于 `com.abilix.controller.api.Protocol`（含 `MasterUART/TransUART`、`Protocol_Receive_Buffer_Size`、`OFFSET_CRC_VALUE`、`CRC value mismatch` 等常量/字符串）。

**【推断/关键】** 用户程序（Python 或 C）**只能通过高层 API**（`SetDO`/`GetAI`/`SetEE`/`GetEE`/传感器函数…）让 MTK 向 STM32 发命令；Python/积木层**没有**"把某个 I/O 口配置成串口并收发任意字节"的 API；C API 层有一套未公开的"原始帧读写"退路（§2.4A），但也只是对本机 STM32 的帧，不是对另一块板。

**【事实】（APK 逆向，详见 `双板通讯研究/分报告_APK与串口协议.md`）** 板内串口协议的关键参数：

| 项 | BlocklyC（Chart C 运行端） | Controller（主 APP；机型 6F=111=SKCON9） |
|---|---|---|
| 串口 | `/dev/ttyMT1` @ 1,000,000 | `/dev/ttyMT1` @ **2,000,000**（主链路）+ `/dev/ttyMT0` @ 1,000,000（**PC 下装/升级通道**，不是用户透明串口） |
| 下行帧（MTK→STM32） | `AA 55` + len + **40B 定长**，校验=8 位累加和 | `AA 55` + 序号 1~4 循环 + len **32B**，[31]=累加和 |
| 上行帧（STM32→MTK） | `BB 66` + **40B**，校验=累加和 | `BB 66` + **72B**，[71]=累加和 |
| 传感器数据 | **每帧广播** AI0..7 / AII0..7 / 颜色 / 4 编码器 | **每帧广播** AI(12 位半字节) / 编码器 / 陀螺 / 电量 / 版本 / 扩展载荷 |
| 时序 | 主循环 ≈10~20ms/帧（8ms 接收窗，编码器 10ms/电量 3s 节流） | 2M 波特率 + 4 组载荷轮换，传感器刷新约每 4 帧一次（实际受主循环） |

→ **传感器值不是"发命令-等回包"，而是 STM32 每帧广播、APP 只读缓存**（所以采样率上限≈帧率，而不是"每个传感器都阻塞等待"）【事实】。这一点把方向2 的"接收采样速度"从"未知阻塞"升级为"≈10~20ms 一帧、50~100Hz 上限"。`GetGray/GetUltraSonic/GetColor/getAI` 类 API 都只是取最近一帧的缓存。

### 1.6 `get_ee/set_ee`（"读写数据"）到底是什么

**【事实】**（手册 p16 "3.6 读写数据"）：

> "读写数据：可存储整形数据，开关机数据不会丢失。**共计 128 个数据**。所有数据均可在界面中修改并保存，也可以通过编程软件进行读写。"

**【事实】** 生成器把积木译为 `robot.get_ee(address)` / `robot.set_ee(address, value)`，地址输入框范围 **1~128**；`set_ee` 的数值被 `robot.clamp(value, -99999, 99999)` 约束（`逆向资料/关键源码/myrobotrun.js:1455-1486`、`myrobotpythoncode.js:543/552`）；机器人界面有独立的"读写数据"页（APK 中 `DataActivity`/`activity_data.xml`、`dialog_data_editor.xml`）。

**【事实】** 这 128 个槽是**每块板各自的本地数据**：主程序用它存灰度标定值（`robot.get_ee(9)/get_ee(10)`，见 `主程序.py:852-853`）；官方"环境采集"会占用 **11~20 号**（11-15 轨迹值、16-20 背景值，手册 p31），做实验时**避开 11~20**（本报告实验程序把探测结果写到 100 起）。

**【结论】它只是"本机 128 个掉电保存的整数格子"，不是内存地址、不是寄存器、也不存在跨板寻址空间。**

**【事实补充：EEPROM 物理位置】** 数据槽实际存放在 **STM32 内部 FLASH**（约 `0x0801F000` 起的最后数页，128×32B 与"128 个数据"吻合）。证据：STM32 固件含完整内部 FLASH 解锁/页擦除/半字编程例程（KEYR `0x45670123/0xCDEF89AB`、`CR|=2` 页擦除、`CR|=1` 半字编程），且引用高地址字面量 `0x0801F108/0x0801F1A0`；`SetEE/GetEE` 在 Java 侧分派到 AIDL 服务（`getData/setData`）→ 走 ttyMT1 协议到 STM32。→ **它只挂在"本板"STM32 上，端口线不会把这块存储暴露出去**（`分报告_STM32固件与串口协议.md` 结论 5/7）。

## 2. 方向1 深入分析：端口直连与"读/改对方地址"

### 2.1 用户设想的拆解

用户设想 = "A 板通过端口线，读写 B 板的数据地址" ≈ 把 `get_ee/set_ee` 当成一个**跨板内存访问通道**。这条链路需要同时满足 4 个条件：

| 环节 | 需要什么 | 实际有没有 | 证据 |
|---|---|---|---|
| ① 物理层 | 两板之间有一条双向数据总线（且 B 的存储器能挂上去） | ❌ 端口只是 STM32 的 GPIO/ADC/UART/I²C 复用口，不接存储总线 | 手册 p6；§1.5 |
| ② 链路层 | 有"从机模式"或"远程寄存器访问"协议 | ❌ 固件是**主机侧**：它去轮询/识别挂在口上的传感器，用户程序只能发高层命令 | §1.5；STM32 分报告 |
| ③ 应用层 | Python/C API 能发"读 B 地址"命令 | ❌ 80 个 API 里没有跨板访问；`get_ee` 只操作本机 | API catalog；§1.6 |
| ④ 存储层 | B 的数据槽在可被外部访问的地址空间里 | ❌ 数据槽在 **B 板 STM32 内部 FLASH**（约 0x0801F000），端口上没有对外 EE 总线窗口 | §1.6、STM32 分报告 |

**四环全缺 → "直接读/篡改对方地址"不可行，且不是"软件没开放"的问题，而是物理与固件层面没有这条路。**

### 2.2 那条 C API 里的 `setSendCmd/getSendCmd/getRecvCmd` 是干什么的？（易误解点）

**【事实】** `Robot.h` 暴露了积木库没有使用的函数（`逆向资料/apk_assets/Robot.h:145-153`）：

```c
//设置发送指令
void setSendCmd(int cmd, int index, int value);
//获取发送指令
int getSendCmd(int cmd, int index);
char *getSendCmdBuffer(int cmd, int index, int length, char *cmdBuffer);
//获取接收指令
int getRecvCmd(int cmd, int index);
char *getRecvCmdBuffer(int cmd, int index, int length, char *cmdBuffer);
```

**【事实】** 机器人端 APK 里对应字符串是 `TRANSACTION_setSendCmd / TRANSACTION_getSendCmd / TRANSACTION_getRecvCmd / TRANSACTION_getSendCmdBuffer / TRANSACTION_getRecvCmdBuffer`（`_分析临时/stm32分析/07_dex_focus.txt`），与 `0x0xxx` 一类命令字一起由 `Protocol`（MTK↔STM32 串口协议）承载。

**【推断】** 这是**"上位机/APP ↔ 机器人程序"的指令邮箱通道**（官方 PC 软件/Chart 的"联机"功能用它给机器人程序传指令/读回值），**不是"主板 A ↔ 主板 B"的通道**。所以它不能用来"读 B 的地址"。

**【已查明（STM32 分报告）】** 这批通道只操作"板内帧缓存"：`setSendCmd` 写某槽固定偏移、`setTTLCmd` 写槽 4、`getRecvCmd*` 读上行帧；STM32 按固定槽语义处理，**没有把这些字节转发到 I/O 口 UART 的代码**。从 Python 用 `ctypes` 调 `libRobot.so` 里的 C 函数属于"进阶研究"，但即便成功，发出的也只是**本机 STM32 命令**，不能读/改另一块板。详见 §2.4A。

### 2.3 可行的端口直连方案：DO → AI/DI 单线 bit-bang

#### 2.3.1 原理

```
A 板 I/O 端口1  ──(GND)────  B 板 I/O 端口1
A 板 I/O 端口1  ──(SIG)────  B 板 I/O 端口1

A 程序：robot.set_do(1, 1)  →  SIG 拉高（≈3.3V/5V，待实测）
        robot.set_do(1, 0)  →  SIG 拉低（0V）
B 程序：robot.get_ai(1)     →  读到高/低对应的数值（0~4095，待实测）
        或 robot.get_touch(1)→ 读到 1/0（干净数字量时更好）
```

- `set_do` 是**用户可用的数字输出**（手册/API 均确认端口 1~12，非阻塞）；
- `get_ai` 是**用户可用的通用模拟输入**（API 文档原话："供自定义传感器使用"）；
- 两者都是高层 API，**不需要裸串口、不需要固件特殊支持** → 这是最接近"一条线连两板"且**确定可编程**的路径。

#### 2.3.2 电气与接线（**安全红线**）

⚠️ **不要用普通 6P6C RJ11 直通线对插两块板的 I/O 口**：该口含 VCC 针，两个电源输出顶牛可能烧端口。正确做法（详见 `实验/00_接线与安全测量.md`）：

1. 万用表测出一个端口的 **GND 针**（断电通断档，对电池负极/USB 外壳）与 **SIG 针**（上电后随 `set_do` 跳变的针）；
2. 自制线：**只连通 GND↔GND、SIG↔SIG**，其余 4 针悬空；
3. 上电前复查：两板 GND 互通、两板 SIG 互通、**两板 VCC 之间必须开路**；
4. 先慢后快（先 0.1s/位），实验期间不要热插拔。

#### 2.3.3 协议设计（半双工，两板都能发）

建议的报文格式（`实验02` 程序已实现最简版）：

```
[同步头: 8 个 1] [起始位: 0] [8 位数据 LSB first] [校验: 异或] [结束位: 1]
编码：位宽 BIT_DT（先 50ms，逐步降到 10~20ms，视实测稳定性）
速率：1/位宽；BIT_DT=50ms → 20 bit/s；BIT_DT=10ms → 100 bit/s（上限由 API 往返延迟决定，待实测）
```

半双工做法：双方默认"监听"，要发时先发同步头，对方检测到同步头后进入接收；发完回监听。握手可用"ACK=回 1 个 0 脉冲"。

#### 2.3.4 速率上限由什么决定（待实测项）

- 每 1 bit 至少需要 **A 一次 `set_do` + B 一次 `get_ai`**；
- 一次 API 调用 = Python → JNI/串口帧 → STM32 → 回包，**单次往返时间未知**（可能在 1~10ms 量级；参考：生成程序里普遍用 `time.sleep(0.01)` 做轮询，说明 10ms 级动作是常规节奏）；
- 因此 **10~100 bit/s 是合理预期**，够传"指令/参数/坐标"，不适合传图片/声音；要高速就用 WiFi。

#### 2.3.5 实验程序
- 发送端：`双板通讯研究/实验/实验02_端口单线_发送端A.py`
- 接收端：`双板通讯研究/实验/实验02_端口单线_接收端B.py`（先 monitor 看读数，再 decode）

### 2.4 其他"端口"路径的逐项判定

| 路径 | 判定 | 依据 |
|---|---|---|
| 端口 **UART**（手册说 10 路支持 UART） | ❌ 用户层**没有**配置 UART/收发的 API【事实】；C API 的"原始字节注入"通道经固件逆向确认**没有转发到 I/O 口 UART 的分支**（§2.4A）→ 用户程序无法把端口变成串口 | API catalog 无 uart/send/recv 方法；§2.4A、STM32 分报告 |
| 端口 **I²C**（2 路可复用） | ❌ 无用户 API；且从机地址/时序不可控 | 同上 |
| 端口 **DI/DO** | ✅ 有 API（`get_touch`/`set_do`）→ 本报告方案 | §2.3 |
| **SERVO 485 总线** | ❌ 两板都是主机，双主冲突；用户 API 只有 `set_servo`（控制智能电机），无裸 485 | Robot.h `SetServo`；手册 p6 |
| **电机口 A~D** | ❌ 7.4V 功率输出，直连必烧 I/O；不可作通讯 | 手册 p6；`00_接线与安全测量.md` |
| **USB-C** | ❌ 两板都是"设备口"（接 PC 用），互连无协议 | 手册 p6/p20 |
| **AI 模块口 USB-A** | ❌ 主机口，接图像/语音模块 | 手册 p6 |
| **WiFi** | ✅ **推荐备选**（若 socket 可用）：两板同网 TCP/UDP；见 §4 与实验08 | §1.3、实验05 |

### 2.4A 隐藏的"原始字节注入"通道：查清了，但不通两板

本次 APK + STM32 固件逆向在底层发现了几条"可以发自定义字节"的通道，**已逐条查清（详见 `分报告_APK与串口协议.md` §4.5、`分报告_STM32固件与串口协议.md` 结论 1-8）**：

| # | 通道 | 实际能力 | 最终判定 |
|---|---|---|---|
| 1 | C API `setSendCmd(cmd,index,value)` / `getSendCmd` / `getRecvCmd*` | 只把 1 字节写进**板内 32B 下行帧固定槽位载荷**的固定偏移（`sendCmdTemp[slot][idx-10]`）；读的也是板上行帧缓存 | ❌ 对端是本机 STM32，不是另一块板 |
| 2 | `setTTLCmd(byte[])`（C API `setSendCmdBuffer` 一类） | 把字节数组写进**槽 4 载荷**（`sendCmdTemp[3]`，19B） | ❌ STM32 对槽 4 走固定语义处理，**反汇编未见"把载荷原样转发到 I/O 口 UART"的分支**（4 组槽处理函数均为内部外设处理） |
| 3 | `TransSerial` = `/dev/ttyMT0` @1M | 不是"任意透明串口"：它是 **PC 下装/升级通道**（先 3 字节握手 → 进入 PC 下载 → zip 落盘） | ❌ 面向 PC，不是用户程序可用的通用串口 |

**【关键判断（已由 STM32 反汇编证实）】** 用户程序（Python 或 C）**没有任何路径**把 12 个 I/O 口变成"自由收发的自定义串口"，也没有"端口 UART 透传"的固件分支；两板端口直连**不能**互通任意字节。
→ 方向1 唯一可行的端口用法，就是 §2.3 的 **`set_do` → `get_ai/get_touch` 电平级 bit-bang**（本质是"约定信号"而非串口协议）。

> 注：STM32 固件确实引用了 USART1/2/3（USART2 疑为 MTK 主链路），端口 12 路"UART×10"的硬件复用细节未完全解出（反汇编未引用 I²C/ADC 基址，相关函数在 0x08007200-0x08007F00 未展开）——这**不改变"没有用户可见透传路径"的结论**，但意味着"端口模式细节"仍有未解部分。【未解/待实测】

### 2.5 方向1 结论

1. **"A 直接读/篡改 B 的数据地址"：不可行**——不是权限问题，是**没有这条总线/协议/地址空间**。四层论证见 §2.1；STM32 固件层也确认：EEPROM 在各自 STM32 内部 FLASH（约 0x0801F000 起、128×32B），**端口上没有对外 EE 总线窗口**，固件里也没有"转发到端口 UART"的分支（`分报告_STM32固件与串口协议.md` 结论 6-8）。
2. **"一个端口 + 一条自制线，两板传数据"：可行**——用 `set_do`→`get_ai/get_touch` 的 bit-bang 链路，这是唯一纯靠现有 Python API、且符合"端口直连"设想的方案（能否成立取决于"空置端口能否读到外部电平"这一实测点）。
3. **"更底层的串口级两板通讯"：目前固件不支持**——C 程序确实能把自定义字节注入板内帧载荷（§2.4A），但 STM32 固件没有把它转发到 I/O 口的路径；要提速只能靠 WiFi（§4）或改固件（不建议）。
4. 若目标是**比赛里两板协同**，**优先用 WiFi（§4）**，端口线只作为"主办方不允许无线/现场无网"时的保底方案。
5. 想"让 B 改自己的数据"：通讯建立后完全可以（A 发命令、B 收命令后自己 `set_ee`）——这是**应用层协议**，不是远程内存写入。

## 3. 方向2 深入分析：传感器/光/声链路

### 3.1 "既能收又能发"的传感器：哪些是真的？

**【事实】** 从手册、积木库、C API、真机 `libRobot.so` 的传感器类型枚举（`AI_TYPE_*`：UNKNOWN/GRAY/MGRAY/COLLISION/ULTRASONIC/FLAME/TEMPERATURE/MAGNETIC_SWITCH/HUMIDITY/INFRARED/ANGLE/LIGHT/COLOR/SOUND_INTENSITY/LED/SMART_LED/ELECTROMAGNET）看，外置传感器可分为三类：

| 类别 | 传感器 | 是否含"发射器" | 用户可控发射？ | 说明 |
|---|---|---|---|---|
| **收发一体（真）** | 灰度 | ✅ 红外 LED + 光敏管 | ❓ 由固件在采样时驱动，用户程序只能通过"读取"间接影响 | 反射式；对射/近距离可被另一板的光敏/红外传感器看到 |
| | 颜色 | ✅ RGB LED + 光电二极管（光敏模式 0~4095） | ❓ 同上 | 发射白光用于测色；近距离可当光源 |
| | 红外（测距） | ✅ 红外 LED + PSD 接收 | ❓ 通常常发/按采样发 | 手册量程 0~1200（mm 待实测）；两个对射可能互测到 |
| | 超声波 | ✅ 压电换能器（发 40kHz + 收回声） | ⚠️ 读取时触发一次 burst；对射可被对方"听到" | 手册 50~1500；两个对射会互相干扰，需编码/时分 |
| **只收不发** | 火焰 | ❌（一般是红外光敏管） | — | 可当红外接收器，接收灰度/红外/智能灯的光 |
| | 光敏 | ❌ | — | **最理想的光接收器**（0~4095） |
| | 碰撞/温度/湿度/磁敏/角度 | ❌（机械/模拟/霍尔/电位器） | — | 与通讯无关 |
| **只发不收** | 彩灯（数字口） | ✅ 通断控制 | ✅ **完全可控**（`set_do` 0/1） | 最可靠的光发射器 |
| | 智能灯 | ✅ RGB | ✅ 可控（常亮/闪烁/呼吸，周期 0.1~10s 级） | 可做 OOK/慢速调制 |
| | 扬声器 | ✅ 声音 | ✅ 可控（内置音频/音符） | 声链路发射 |
| | 屏幕 | ✅ 光（3.5寸彩屏） | ✅ 可控（显示内容/表情） | 大面光源，可远距离被光敏接收（待实测显示底色控制） |
| **内置接收** | 麦克风 | — | — | 声链路接收（`get_mic`） |

**所以"传感器既能收又能发"严格说只对"灰度/颜色/红外/超声"成立**；但**通讯可靠性最高的是"彩灯/LED/屏幕/扬声器（发） + 光敏/火焰/麦克风（收）"**——因为发射完全由用户程序控制。

| 1b | ~~WiFi TCP/UDP（纯 Python）~~ | ~~Python socket~~ | — | — | ~~最快~~ | ❌ **已实测 socket=0，不可用**；需 C 程序/安卓改造 | 实验05（已做） |
| 2 | **声音** | 扬声器 `play/play_until` | 麦克风 `get_mic` | 几 bit/s | 零外设、零接线、当天可验 | 环境噪声、mp3 播放延迟、速率低 | 实验01 |
| 3 | **端口电链路** | `set_do` | `get_ai/get_touch` | 10~几百 bit/s | 有 API 保证、抗光/声干扰 | 需自制线+测量；RJ11 引脚不明 | 实验02 |

### 3.3 光链路设计要点（执行器发、传感器收）

- **发射端**（A）：
  - 彩灯/LED：`set_do(port, 1/0)`，通断干净；位宽 10ms 级（由 Python 时序决定，待实测）；
  - 智能灯：`smart_led(port, 1, 0, 255,255,255)` / `smart_led(port, 0, 0, 0,0,0)`（常亮模式；闪烁/呼吸由灯内部定时，**不适合精确调制**）；
- **接收端**（B）：
  - 光敏 `get_light`（推荐，0~4095）；
  - 颜色传感器需在"光敏模式"（手册 p13，0~4095）——模式可能需在传感器上手动切换【待实测】；
  - 灰度/火焰可当"红外/近红外接收器"（若 A 用红外源，如灰度传感器自身/红外 LED）；
- **同步与编码**：先发 6~8 个"亮"位作同步头；用**脉宽编码**（亮 2 倍/1 倍时长表示 1/0）比纯 OOK 更抗环境光；再加 1 字节校验。
- **摆放**：灯正对光敏，距离 0.5~10cm 起步；避免阳光/顶灯直射光敏；实验在桌下/纸盒内做更稳。

**【重要修正（来自方向2 分报告，`分报告_方向2_传感器与光声链路.md` §1.2/§3）】** 不要高估这些链路，有三个硬约束：
1. **所有接收 API 只返回标量**（`get_light`/`get_gray`/`get_flame`/`get_ai`/`get_mic` 都是强度，`get_ultra_sonic`/`get_infrared` 是距离）——**没有频谱/相位**，所以一切链路只能是 OOK/事件调制，**不能 FSK**；声音链路也**不能靠音高区分 0/1**（只有声强）。
2. **唯一能做"任意脉宽"的接口是 `set_do`**；`smart_led` 是"下发配置让灯自己跑"（闪烁/呼吸由灯内硬件执行，周期只能 0~10 秒级），只能做慢速/信标；屏幕 API 只有 `print/clear/print_expression`，**不能直接画纯白/纯黑整屏**（`clear()` 底色待实测）。
3. **速率天花板不是物理带宽**，而是"Python→固件→STM32→回帧"的往返与帧周期（本次确认帧周期约 10~20ms 量级）→ 光/声链路实际速率只有 **10~100 bps 量级**，适合传命令/状态，不适合传数据流。

### 3.4 "传感器自身发射"到底能不能通讯？（本方向最需要真机验证的点）

这是用户说的"传感器漏洞"核心。判定要点：

1. **发射器是否真的存在**：灰度/颜色/红外/超声的模块内部确实有 LED/换能器（【推断】，由传感器原理与手册返回值推断；真机拆解可确认）。
2. **发射时机是否可控**：
   - 对**被动模拟传感器**（灰度/光敏/火焰），发射 LED 可能由端口 VCC 直接供电（常亮）→ **无法调制**，只能"收"；
   - 对**智能传感器**（超声/红外/颜色，走 UART/协议），发射由固件命令触发——如果**每次 `get_xxx()` 调用触发一次测量（含一次发射 burst）**，那么"调用的时机"就能调制出一串光/声脉冲 → **可通讯**（速率 = 用户调用 `get_xxx` 的频率，可能 10~50 次/s）。
   - 关键证据在 STM32 固件（`stm32.bin`）与 `libRobot.so` 的采样命令；见 **`双板通讯研究/分报告_STM32固件与串口协议.md`**（本次研究已逆向，结论汇总附后）。
3. **对方能否"听到"**：两个同型传感器面对面时，A 的发射会被 B 的接收器直接照到（近距离），B 的读数会出现"近距离/超量程/异常值"→ 可当 1 位信息。
4. **工程现实**：即使成立，速率低、易受干扰、两个传感器互相发射会自扰（尤其超声），**不建议作为比赛主通讯**，可作为"展示/研究"用途。

**【固件层最终结论（`分报告_STM32固件与串口协议.md` 结论 6/9）】** STM32 对 12 口是**自主轮询采样**：MTK 每 ≥1.5ms 发一帧命令，STM32 每帧回全部传感器/状态值；用户 `get_gray`/`get_ultra_sonic`/`get_color` **只是读最近一帧缓存，读取时刻并不触发发射**；固件里也**没有"端口自定义串口/透传"分支**。→ "传感器自身发射"若要通讯，前提是"发射时机可由用户控制"，**目前没有证据支持**；若某传感器 LED 是常亮供电，则只能"收"不能"发"，链路根本不存在。建议仍做 §3.4 的黑盒实验（灰度对射/超声互扰）作为最终验证，但**不要把比赛方案建立在它上面**。

### 3.5 方向2 结论

1. **"两板光/声通讯"确定可行**（执行器发+传感器收），首推**声音链路最快验证**，其次**光链路/端口电链路**；
2. **"传感器自身收发一体"原理成立**，但**能否调制取决于固件**，属于进阶验证项；本报告已给出实验路径与判据；
3. 原"WiFi 是唯一高速方案"的前提（Python socket）已被实验05 否定；现在高速路线 = **USB-C 有线/PC 中继** 或 **C 程序 socket**，光/声/端口链路作补充或规则受限时的替代（§0.0）。

## 6. 风险、限制与注意事项

### 6.1 电气安全（最重要）
1. **绝不能用普通 RJ11 线直接对插两块板的 I/O 口**：VCC 对 VCC 可能烧端口（详见 §2.3.2 与 `00_接线与安全测量.md`）。
2. **电机口 A~D 是 7.4V 功率输出**，不能与任何信号口/传感器口直连。
3. 接线前断电、上电前复查、先慢速后加速、不热插拔。
4. 实验只接"你的两块板"，不要接到场地/其他设备上。

### 6.2 EEPROM 使用注意
- 128 个槽位，**11~20 被官方环境采集占用**，不要覆盖；
- `set_ee` 有擦写寿命，**不要放在循环里**（本报告实验只在探测时写一次）；探测结果写 100 起。

### 6.3 运行环境风险
- 机器人端 Python 是 CPython 3.4：**不支持 f-string、类型注解等新语法**；实验程序已按 3.4 兼容写法（简单字符串拼接）；
- 官方文档建议只 import `time/libstarpy/math`；实验05 已判 **socket/math/random 等不可用**（不要硬试，程序里要 try/except）；机器人端只有静态 C 模块 + 纯 Python stdlib。
- 机器人系统/APP 可能自动更新（`BrainApkUpgrade`、`AbilixUpdate`），逆向结论以更新前版本为准。

### 6.4 比赛规则（须自行确认）
- 两板通讯/双机器人协同是否被 WER 2026 普及赛规则允许，**不属于本报告技术范围**；若规则禁止无线/双板联动，请只用技术结论、不要上场使用。技术可行 ≠ 允许使用。

### 6.5 "数据篡改"的伦理边界
- 本报告结论是"**无法远程读写对方主板存储**"，因此不存在"篡改对手设备"的技术路径；所有可行方案都是"两板之间约定的通讯协议"，不涉及攻击/破坏他人设备。
