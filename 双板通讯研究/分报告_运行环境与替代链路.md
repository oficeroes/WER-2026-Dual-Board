## 0. 结论摘要（先看这里）

1. **机器人端 Python 在 Android 侧的“大脑 APP”里执行，不是 STM32、也不是 PC**。SKCON9 的大脑 APP 是 `6F/Controller_43.apk`（包名 `com.abilix.controller`，versionName 1.0.43，对应机型值 111=0x6F），通过 `ProgramAndInterfacePython` + 独立的 StarCore（srplab）运行时执行用户 `.py`。**【事实】**（`_分析临时/apk分析/提取/manifest_Controller6F.xml:1-51`、`.../disasm_C_com_abilix_utils_ProgramAndInterfacePython.txt:76-84`）
2. **Python 版本是 CPython 3.4**：运行时库在系统分区 `/system/lib/python/libpython3.4m.so` + `python3.4.zip`。**【事实/强证据】**（`_分析临时/研究证据/运行环境/controller43_6F/dex_strings_all.txt:2328-2330`；实际 `sys.version` 以探测程序为准）
3. `libstarpy` 是**机器人端 Python 模块**（绑定 StarCore/机器人 API），`Robot` 类由运行时注入全局；PC 上没有。**【事实】**（同上 `:774-780,38629`；`WER_VSCode_工具/python-stubs/README.md:43-79`）
4. 官方 PC 软件的“编译”**只是语法检查**（PC 自带 Python 3.7.3 跑 `-m compileall`），**不检查 import、不执行代码、不产生下载物**；下载的是 `.py` 源码 zip。**【事实】**（`逆向资料/decompiled/Assembly-CSharp.decompiled.cs:92081,92097-92141,120317-120331`；`逆向资料/下载分析/下载链路逆向.md:139-145`）
5. **“下载的 .py 能否 import socket/os/threading”目前无法从静态证据下定论**：Python 是 3.4、stdlib 打包在 `python3.4.zip`，`socket` 依赖 `_socket` 扩展；只能真机探测。→ 已给出可直接下载的探测程序 `_分析临时/研究证据/运行环境/探测_import与环境.py`。**【待实测】**
6. 两板通讯的**第一优先路线：WiFi 直连（两板同一 2.4G 路由器，或一板热点一板连）**，用 Python `socket` 做 TCP/UDP；前提 = socket 可 import + 知道双方 IP + 路由器未开 AP 隔离。**【待实测】**
7. **第二路线：PC 中转**（两板都连 PC；需 socket。若 ADB 可用，`adb reverse` 可把“板→PC”变成 wired 高可靠链路）。**若 socket 不可用，官方下载链路只能做单向、非实时文件注入，不能实时互传。**
8. **ADB/USB 路线大概率不可用**：两个机器人端 APP 都是 release（`debuggable=false`/无 debuggable 属性）；官方“USB 有线下载”实际走串口（`LibUart`），PC 自带 `adb.exe` 但 Assembly-CSharp 无任何调用点。→ 接真机后按 §C3 步骤先判断设备形态。**【事实+待实测】**
9. **蓝牙不可用**（无用户 API、Python 3.4 stdlib 无蓝牙模块）；**USB-A 口是 USB Host（接 AI 模块），两板不能 Host-Host 直连**；**AP+STA 同时开**官方 UI 未提供、MTK6580 平台通常不支持。**【事实/推断/待实测】**
10. 额外发现（潜在强通道）：C 程序在**机器人本机用 `gcc4.8.2` 编译成 `.so` 再执行**（apk-dex 证据）。若“自定义 .c 下载”可行，C 代码可直接调用 libc socket，从根上绕过 Python 的 import 限制。**【推断，高风险/待验证，且需注意合规】**

**最终建议（供 Lead 决策）**：先花 20 分钟做“探测程序 + 两板同网 TCP 样例”真机验证；WiFi socket 通 → 走 WiFi 直连；socket 不通 → 评估 PC 中转（WiFi 或 ADB reverse）；两者都不行才退回方向1/2 的端口/传感器链路（带宽极低，只做慢速状态同步）。

### A.5 程序结束后数据（EEPROM）如何保留（【事实】）

- SKCON9 有 128 个“读写数据”槽，关机不丢；可在屏幕界面读写，或编程软件读写（手册 `:381-384`）。
- Python API：`robot.set_ee(address, value)` / `robot.get_ee(address)`（`WER_VSCode_工具/python-stubs/libstarpy.pyi:667,681`）。**这是两板之间“离线交换”最廉价的中转存储**：如 PC 依次连两板，或两板各自程序运行期间用 EEPROM 暂存状态（掉电保存）。
- 注意：EEPROM 在 STM32 侧（由 ttyMT1 协议读写），**不具备“另一块板远程读”的能力**（方向1 报告会论证），它只是本机持久存储。

## B. 下载的 .py 能否 import 任意模块？（核心开放问题）

### B.1 先看官方软件到底检查了什么（【事实】）

| 环节 | 做了什么 | 证据 |
|---|---|---|
| 编译按钮 | 把当前代码写 `StreamingAssets\pythoncompile\code\main.py`（UTF-8 带 BOM），用 **PC 自带 Python 3.7.3** 执行 `python.exe -m compileall "...\code\main.py"` | `逆向资料/decompiled/Assembly-CSharp.decompiled.cs:92081,92097-92141,120317-120331` |
| 下载 | 发送 `<程序名>.py.zip`（zip 内条目 `<名>.py/<名>.py`，内容是 **.py 源码**） | `逆向资料/下载分析/下载链路逆向.md:21,27,79-95` |
| import 检查 | **没有**。compileall 只编译（语法）不执行，不解析 import 是否可满足；C# 中无 import 白名单/扫描代码 | 同上 + 全库 grep 结果 |

三个直接影响：
1. `import socket` 之类**能通过官方“编译”**（语法正确即可），失败只会在机器人运行时 `ImportError`；
2. PC 检查器是 **3.7.3**，机器人是 **3.4** → 用了 f-string（3.6+）、`async/await`（3.5+）、`:=`（3.8）等新语法会“PC 检查通过、机器人挂掉”。**写机器人代码请按 Python 3.4 语法**（用 `%` 格式化、不用 f-string）；
3. “白名单 time/libstarpy/math、不要 import 第三方库”只是文档约定（`WER机器人代码生成_给AI的说明书.md:226,413`），**不是软件拦截**。

### B.2 socket 等模块的可用性判断

- 机器人 Python = CPython 3.4 + `/system/lib/python/python3.4.zip`（标准库 zip）。**【事实/强证据】**
- `socket` 是纯 Python 模块 + `_socket` C 扩展；`os/threading/time/struct/select` 多为纯 Python 或内建。3.4 的移动端裁剪版是否保留 `_socket` 必须实测。**【推断/待实测】**
- 风险排序（推断）：`socket`（可能可用，关键）、`os/threading/time/json/struct/select/re`（大概率可用）、`subprocess/ctypes/ssl/sqlite3`（大概率不可用/不完整）。
- 如果 `socket` 不可用还有没有网络能力？从 `libstarpy` 的 API 存根看，它只暴露机器人方法（无网络/无 socket，`WER_VSCode_工具/python-stubs/libstarpy.pyi`）；但 StarCore 引擎本身在 Java 层有 `_SetupSocketServer/_SetupSocketClient/_UDPRecv/_HttpServer/_ShellExecute` 等能力（`.../dex_strings_all.txt:29526-29573,24414-24456`），**是否被 libstarpy 暴露给 Python 完全未知**——探测程序已包含 `hasattr(libstarpy,'SrvGroup')` 等检查（地址 42-43）。

### B.3 最小探测程序（已写现成文件，待真机验证）

- 程序：`_分析临时/研究证据/运行环境/探测_import与环境.py`（文件头 `#<SKCON9><WiFi><ProbeEnv>`，下载时程序名写 **ProbeEnv**）。
- 逐项探测并写入 EEPROM：`1-3` Python 版本、`10-33` 24 个 stdlib 模块 import、`40-46` libstarpy 形态、`50-55` socket 能力、`60-61` threading 是否真跑、`70-72` 文件可写性；同时 `robot.print` 到屏幕并打印 `sys.version/sys.path/local_ip/cwd`。
- 读结果：程序 `读回_EEPROM结果.py`（下载为 **ProbeRead**，把 1..74 逐条打印到屏幕拍照）；或机器人屏幕“读写数据”页面直接看地址 1-74。**【待实测】**
- 若 socket 可用，探测程序还会打印 `LOCAL_IP`（UDP connect 技巧）——这同时解决“怎么知道板子 IP”。

## C. 两板通讯替代链路评估

> 共同前提：所有样例都遵守官方骨架（`#<SKCON9><WiFi><名字>` + `import time` + `import libstarpy` + `robot = Robot()` + `main()`），程序名与文件头/下载名一致；端口避开官方 10086/8890/7777/9999。

### C1. 首选：WiFi 直连（TCP/UDP）

**两种组网方式**
1. **同路由器（推荐）**：两板都做 STA 连同一 2.4G 路由器；PC 也在同网段用于调试。要求路由器**关闭 AP 隔离/客户端隔离**（否则两板互不可达），2.4G 频段。
2. **一板热点 + 一板连**：A 板 设置→热点 打开（名称随“设置-名称”，密码可改，手册 `:397-400`）；B 板 设置→WLAN 连 A 板热点。A 板作为热点网关，其 IP 大概率 `192.168.43.1`（Android 热点默认段，**【推断/待实测】**），B 板为 `192.168.43.x`。

**IP 怎么获得（按可靠性排序）**
1. **机器人屏幕**：设置 APP 含 WifiFragment/WifiSupport 与 `IP = `、`IP_ADDRESS` 字符串（`_分析临时/研究证据/运行环境/03_AbilixSetting_25_IP与WLAN字符串.txt`）→ 设置→WLAN 界面应能看本机 IP。**【待实测具体位置】**
2. **路由器后台 DHCP 客户端列表**（同路由器模式）。
3. **PC 扫描**：官方 VSCode 工具已有 `WER: 扫描局域网机器人 IP`（TCP 10086 探测，`WER_VSCode_工具/README_使用说明.md:37-45`）；也可 `Test-NetConnection <IP> -Port 10086/8890`。
4. **程序内自发现**：`样例_UDP发现IP.py`（每板广播 `WHO:<自己IP>` 到 255.255.255.255:8867 并监听；AP 隔离会失败）；或 UDP connect 8.8.8.8 拿自己 IP。
5. 官方协议里另有 UDP 发现：PC 发 7777、机器人回 `160,255`+IP 到 9999（`逆向资料/下载分析/协议规格.md:407-435`、`逆向资料/decompiled/Assembly-CSharp.decompiled.cs:109990-110209`）。机器人 Controller 里确有 `UDP_LISTENING_PORT_7777/UDP_SENDING_PORT_9999` 常量（`.../dex_strings_all.txt:26358-26359`）——**说明板子本就有 UDP 网络栈；但这是官方下载服务的端口，不建议用户程序去占用/干扰，仅可作为“发现思路”参考**。**【事实+待实测】**

**样例程序（已写现成文件）**
- A 板服务端：`_分析临时/研究证据/运行环境/样例_两板TCP_A板服务端.py`（端口 8866，`accept`+每连接一个 `threading.Thread`，行协议 `B,<seq>,<value>\n` → 回 `A,<seq>,OK\n`，收到值写 EEPROM 100）。
- B 板客户端：`样例_两板TCP_B板客户端.py`（`socket.create_connection` 超时 3s、断线 2s 重连、发送传感器值 `robot.get_ai(1)`）。
- UDP 发现：`样例_UDP发现IP.py`。

**协议设计建议（实用）**
- 行协议或 `[AA 55][len][seq][payload][CRC16]` 二进制；带 seq/ack、超时重发（≤3 次）、心跳（1s）、重连退避（1-2s）。
- 机器人是单入口 main()：**通讯放后台线程，主线程照常跑机器人逻辑**（官方模板本身 import threading；需实测线程是否真并发，探测地址 60）。
- 调试靠 `robot.print`：把关键状态打印到 3.5" 屏（拍照），或写 EEPROM 再读。
- 速率预期（**【推断】**，必须实测）：2.4G WiFi 物理层够用，但 Python 线程+GIL+机器人调度下，小包往返延迟约 **20-100ms**、有效吞吐约 **1-50 KB/s**；对“状态同步/少量传感器值/指令”足够，对图像/音频不够。
- 风险：AP 隔离、2.4G 干扰、DHCP 换 IP、WiFi 省电延迟、`socket` 不可用（最大风险）。

### C2. PC 中转

**适用**：两板不在同一网段/被 AP 隔离/只有一台路由器无法互访；或想集中记录日志。

- **A. WiFi 中转**：两板都连 PC 所在网络并**主动连 PC**（需要 Python socket）；PC 跑 `_分析临时/研究证据/运行环境/PC中转_双板中继服务器.py`（监听 9001/9002，双向转发）。注意：官方下载链路里机器人是**服务端**（10086/8890），PC 是客户端；反过来“机器人主动连 PC”在本工作里**没有官方功能**，只能靠用户 Python 的 socket。【事实+待实测】
- **B. ADB reverse 中转（若 ADB 可用，最稳）**：两板 USB 接 PC，`adb -s <A> reverse tcp:9001 tcp:9001`、`adb -s <B> reverse tcp:9002 tcp:9002`；板内 Python 连 `127.0.0.1:9001/9002` → 到 PC 中继。优点：不依赖 WiFi、延迟低、可同时供电；缺点：ADB 是否可用未知（§C3）。
- **C. 仅官方下载链路（socket 不可用时的兜底，非实时）**：PC 能主动连板子的 10086/8890，把“数据”塞进一个小 `.py` 程序下载进去（板子下一轮运行该程序读取并执行）——**单向、秒级、每次都重启程序**，只能做“参数/指令下发”，不能实时双向。回传方向：板子无法主动上报（除非 EEPROM 有人去读，而 PC 目前没有读 EEPROM 的能力）→ 兜底价值有限。**【推断】**
- 若 ADB 可用，还有更强做法（仅记录，需合规评估）：`adb install` 装一个自建 helper APK 做 socket/serial 桥；但比赛合规风险高。

### C3. USB-C / ADB 路线（真机验证步骤最全）

**已确认事实**
- 官方“USB 有线下载”实现走 **串口**：`UartManager` → `LibUart.TryConnectSerialPort()`（`逆向资料/decompiled/Assembly-CSharp.decompiled.cs:95826-95890`）；文档对比“WiFi=TCP 两条连接 / USB=串口”，SKCON9 用 `SK9` 类（`逆向资料/下载分析/下载链路逆向.md:473`）。→ **官方 USB 下载不是 ADB。**
- PC 自带 `StreamingAssets\adb\adb.exe`（908,800 B）+ `Constants.COMMANDEXEC="adb.exe"`（`...Assembly-CSharp.decompiled.cs:110817-110819`），但 Assembly-CSharp 全文只有 3 处 `Process.Start`（编译/自升级/自升级），**没有任何调用 adb 的地方** → 本版本大概率未使用。**【事实→推断】**
- 机器人端两个 APP 都**不可调试**：BlocklyC 显式 `debuggable="false"`；Controller_43 无 debuggable 属性（默认 false）。（apk-dex 解析：`_分析临时/apk分析/提取/manifest_BlocklyC.xml:3`、`manifest_Controller6F.xml:1-51`）→ 即使 ADB 可用，`run-as` 也进不去 APP 私有目录。
- 机器人屏幕 APP 是 `com.abilix.controller`（MainActivity=HOME/LAUNCHER）；`AbilixUpdate_1.apk` 等由 brainApk 升级机制管理。

**接真机后如何判断（按顺序做，5 分钟）**
1. **看设备管理器**（机器人开机、USB-C 接 PC）：
   - PowerShell：`Get-PnpDevice -PresentOnly | Where-Object {$_.InstanceId -like 'USB*'} | Select-Object FriendlyName,InstanceId,Status`
   - 若出现 **“Android Composite ADB Interface” / “Android ADB Interface”** → ADB 路线成立；
   - 若出现 **“USB Serial Port (COMx)” / 未知串口设备** → 与“官方 USB 下载走 LibUart 串口”一致，ADB 路线不成立；
   - 记下 **VID/PID**（`InstanceId` 里 `VID_xxxx&PID_xxxx`）便于查驱动/确认。
2. **adb 探测**（本机已有 `C:\platform-tools\adb.exe`，版本 1.0.41 / 37.0.0）：
   - `C:\platform-tools\adb.exe devices` → 有设备则继续；
   - 若显示 `unauthorized`：看机器人屏幕是否弹“允许 USB 调试”对话框（有触摸屏可点允许）；
   - `adb shell id`、`adb shell getprop ro.build.version.release`、`adb shell getprop ro.serialno`。
3. **ADB 可用后的高价值操作**：
   - 调试 Python：`adb logcat | findstr python` —— **能直接看到用户 Python 的 print/traceback**（比拍照强太多）；
   - 读环境：`adb shell ls /system/lib/python`、`adb shell ls -l /dev/ttyMT*`、`adb shell cat /proc/cpuinfo`；
   - 传文件/日志：`adb push/pull`（`/sdcard/Download` 可写）；
   - 截图机器人屏幕（读探测结果神器）：`adb shell screencap -p /sdcard/s.png` + `adb pull /sdcard/s.png`；
   - 端口转发：`adb forward tcp:10086 tcp:10086`（PC 访问板子服务）；`adb reverse tcp:9001 tcp:9001`（板子 Python 访问 PC：**两板 USB 中转的关键**）；
   - 导出 APP 数据：`allowBackup=true`，可试 `adb backup -f ctrl.ab com.abilix.controller`（Android 版本/是否允许需实测）；
   - 不能做：`run-as com.abilix.controller`（非 debuggable 会拒绝）；`adb root` 需 rom 是 userdebug（大概率不行）。
4. **ADB 不可用（只有 COM 口）时**：只能沿用官方串口协议（`AA 55` 帧 + 请求/应答 + CRC）做程序下载；想实时数据交换需逆 `LibUart` 的私有命令通道，成本高，不作为首选。**【推断】**

### C4. 蓝牙（内置）

- 手册只写“内置蓝牙”（`_分析临时/SKCON9手册/SKCON9手册_全文.txt:120-122`），全手册无蓝牙使用说明。
- Controller manifest 有 `BLUETOOTH/BLUETOOTH_ADMIN` 权限 + `uses-feature android.hardware.bluetooth_le required=true`（`_分析临时/apk分析/提取/manifest_Controller6F.xml:12-17`）；设置 APP 里只出现 `BluetoothGattDescriptor` 字符串（`03_AbilixSetting_25_IP与WLAN字符串.txt`），无配对界面证据。
- PC 软件（C# + 解密 Lua）**全文 0 处“蓝牙/Bluetooth”**；`libstarpy` 存根无任何蓝牙 API；CPython 3.4 标准库无蓝牙模块。
- **结论：蓝牙硬件存在，但没有用户可用的 API/积木/运行时模块 → 两板通讯不可用。**【事实/推断】

### C5. 其他通道

| 通道 | 可行性 | 说明 |
|---|---|---|
| USB-A AI 口（图像/语音模块） | 不可行 | 机器人是 USB Host（libusb/UVC，`.../apk_entries.txt` 有 libusb100/libuvc/UVCCamera）；两板都做 Host → Host-Host 需 OTG 转换/特殊线，非用户程序可达。 |
| 双板 USB-C 直连 | 不可行 | USB-C 是设备口（连 PC 下载用），两块设备口不能直连。 |
| AP+STA 同时 | 大概率不可行 | 官方设置只有 WLAN / 热点 两个独立模式；MTK6580/Android7 一般不支持并发 AP+STA。**【推断/待实测】** 替代：一板 AP + 一板 STA（等于 C1 方式2）。 |
| 官方下载链路当数据通道 | 低 | 单向 PC→板、整程序替换、无回传；速率 KB/s 级，秒级延迟；仅“参数下发”用途。**【推断】** |
| **C 程序（机器人本机 gcc）** | 潜在强通道 | apk-dex 证据：Controller 用 `/system/xbin/gcc4.8.2/bin/arm-linux-androideabi-gcc *.c -pie -fPIC -L. -lm -lRobot -shared -o librobot_xxx.so` 本机编译 `.c` → 复制为 `libuser.so` → `libRobot.so` 的 `JCC_Main` 执行。若“自定义 .c 能被下载/编译”，C 代码可直接 `socket()`/`connect()`/`fork` 等，绕过 Python import 限制。**待验证：C 程序下载入口（fileType/Chart3.0 代码模式）、gcc 头文件是否齐全、合规风险。**【推断，建议作为 B 计划】 |
| 端口直连（方向1）/ 传感器（方向2） | 见另两份分报告 | 带宽极低（bit-bang/光/声），只适合慢速状态同步/握手。 |

## D. 两板通讯路线决策树 / 排名表

### D.1 决策树

```
开始
├─ 真机跑 探测程序
│   ├─ socket 可 import ──────────────────────────────┐
│   │   ├─ 两板在同一 2.4G 网络/热点，能互相可达？    │
│   │   │   ├─ 是 → 【路线1】WiFi TCP/UDP 直连（首选）│
│   │   │   └─ 否（AP 隔离/跨网段）→ 【路线2】PC 中转（WiFi）│
│   │   └─ 需要极高可靠性/实时 → 查 ADB（§C3）→ 可用则【路线3】adb reverse 中转
│   └─ socket 不可用 ────────────────────────────────┐
│       ├─ 只是“小数据、低频、可秒级延迟” → 下载链路/EEPROM 间接交换（路线5，勉强）
│       ├─ 需要实时双向 → 只能退回【方向1 端口直连】/【方向2 传感器】链路（极低速）
│       └─ 愿意突破 Python 限制 → 研究 C 程序 gcc 通道（路线4，高成本/合规风险）
└─ 若 ADB 真可用：adb logcat/screencap/forward/reverse 作为所有路线的“调试+兜底”增强
```

## E. 给 Lead 可直接写入最终报告的素材

### E.1 路由器配置步骤（同路由器模式）
1. 用 2.4G WiFi（手册：WLAN 仅 2.4G，`_分析临时/SKCON9手册/SKCON9手册_全文.txt:147`）。
2. 路由器后台：**关闭“AP 隔离/客户端隔离/Wireless Isolation”**；关闭 MAC 过滤；DHCP 保持开启；建议给两块板做 DHCP 静态绑定（IP 固定）。
3. 板 A：设置 → WLAN → 选 SSID → 输密码 → 连上；板 B 同上。
4. 记录两板 IP（设置界面/路由器 DHCP 列表/PC 扫描）。
5. 验证：PC `Test-NetConnection <板IP> -Port 10086` 应通（说明网络/防火墙 OK）；再跑 TCP 样例。

### E.2 热点配置步骤（一板热点 + 一板连）
1. 板 A：设置 → 热点 → 打开（热点名=“设置-名称”，密码可改；改名后通常要重开热点，手册 `:397-400`）。
2. 板 B：设置 → WLAN → 搜到 A 的热点名 → 输密码连接。
3. A 板 IP 预期 `192.168.43.1`（推断），B 板 `192.168.43.x`；以实际显示为准。
4. 注意：热点模式与 WLAN 模式通常二选一；不要同时依赖 A 板连外网。

### E.4 真机验证清单（一次性做完，30 分钟内）
1. 下载并运行 `探测_import与环境.py`（ProbeEnv）→ 屏幕拍照/EEPROM 读取 → 填表：socket/os/threading 是否可用、Python 版本、本机 IP、cwd。
2. 查两板 IP（屏幕/路由器/PC 扫描），PC `Test-NetConnection <IP> -Port 10086`。
3. 下载 `样例_两板TCP_A板服务端.py`(A) 与 `样例_两板TCP_B板客户端.py`(B，改 HOST) → A 屏幕应显 `accept`，B 屏幕应显 `reply`。
4. USB-C 接 PC → 设备管理器 + `adb devices` → 记录设备形态（ADB 接口 vs COM 口）。
5. 若 ADB 可用：`adb logcat`/`screencap` 复跑步骤 1-3（可拿到文本证据）。
6. 极端场景测：路由器开 AP 隔离会怎样；热点模式 IP 是否 192.168.43.1；程序停止方式；长时间运行是否被杀。

### E.5 一句话结论（供摘要）
> SKCON9 的 Python 用户程序由 Android 大脑 APP（Controller_43）+ StarCore + CPython 3.4 执行；官方下载只做语法检查、不限制 import。两板通讯最现实的是“WiFi 直连 Python socket”（需真机确认 socket 可用与 IP）；不行再用 PC 中转；ADB 因 release 构建+USB 实际走串口，大概率不可用；蓝牙/USB 直连不可用。**建议 Lead 把“WiFi socket 探测”列为最高优先级验证项**，并预留“PC 中转/端口-传感器兜底”。
